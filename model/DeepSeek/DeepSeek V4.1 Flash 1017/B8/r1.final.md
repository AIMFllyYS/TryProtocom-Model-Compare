# 交付说明：paydesk（对接 PayGate 支付网关的商户后端）

## 一句话

`paydesk/` 是一个**纯 Python 标准库、零第三方依赖、单进程**的商户后端，实现了题目契约里的全部接口，
并把「不多扣、不少收、不多退」做成了可验证的资金不变量；配套交付了契约测试套件、故障矩阵探针、
变异体验证和完整的决策记录。

## 交付物

```
paydesk/
├── bench.json                  # 启动约定：setup / start / test / health
├── server.py                   # HTTP 入口（路由、统一错误格式、CORS、健康检查）
├── core.py                     # 业务状态机（支付/webhook/退款/对账/崩溃恢复）
├── appstate.py                 # JSON 快照存储（RLock + fsync + 原子替换 + Windows 重试）
├── gateway.py                  # PayGate 客户端（未处理 / 不确定 / 业务错误 三分类）
├── SPEC.md                     # 契约的可执行解释（团队权威约定，含所有错误码与边界）
├── README.md                   # 怎么跑、怎么验证、架构
├── DECISIONS.md                # 关键决策、有意不做、已知风险、验证方法

├── tools/
│   ├── setup.py / health.py    # bench.json 的 setup / health 命令
│   ├── smoke.py                # 28 项快速冒烟（含故障与乱序）
│   ├── probe.py                # 17 场景故障矩阵探针（用网关真实计数与金额证明）
│   ├── PROBE-REPORT.md         # 探针的 17 场景证据矩阵
│   └── mutants/                # 变异体验证：注入 8 类常见 bug，证明 tests/ 能抓住（8/8）
```

工作目录下的 `FINAL_MESSAGE.md` 是本文件。

## 怎么运行

```bash
# 1) 网关沙箱
PORT=9100 PROVIDER_KEY=sk_test_bench WEBHOOK_SECRET=whsec_bench python provider-sim/provider.py

# 2) 商户服务（bench.json 的 start 命令，在 paydesk/ 目录下）
PORT=8080 DB_PATH=/tmp/paydesk/db.json \
PROVIDER_URL=http://127.0.0.1:9100 PROVIDER_KEY=sk_test_bench \
WEBHOOK_SECRET=whsec_bench BENCH_MODE=1 \
python server.py

# 3) 健康检查 / 契约测试 / 探针
BASE_URL=http://127.0.0.1:8080 python tools/health.py
BASE_URL=http://127.0.0.1:8080 PROVIDER_URL=http://127.0.0.1:9100 \
WEBHOOK_SECRET=whsec_bench python tests/run_tests.py
BASE_URL=http://127.0.0.1:8080 PROVIDER_URL=http://127.0.0.1:9100 \
WEBHOOK_SECRET=whsec_bench python tools/probe.py
```

`bench.json` 里的命令写成 `python3 X || python X`，兼容 Linux（`python3`）与 Windows（`python`）；
命令假定工作目录是 `paydesk/`，脚本内部用 `__file__` 定位，不依赖 cwd。
网关地址、密钥、webhook 密钥全部来自环境变量（`PROVIDER_URL`/`PROVIDER_KEY`/`WEBHOOK_SECRET`），代码里没有硬编码。

## 核心设计（为什么不会多扣/少收/多退）

1. **确定性网关幂等键**：`pay:<order_id>:sha256(客户端 Idempotency-Key)[:16]`、`refund:<order_id>:sha256(...)`。
   同键重放/并发/网关超时后重试都复用同一个网关幂等键，网关只会重放第一次的结果，**不会创建第二笔扣款/退款**。
2. **支付意图先落盘再调用网关**：状态 `payment_pending` + 网关幂等键在发请求前写入数据文件；
   进程崩溃后恢复为 `payment_unknown`，靠对账收敛，绝不产生重复扣款。
3. **结果不确定就不猜**：网关读超时/连接中断 → `payment_unknown`（202），明确未处理（5xx/429/连接被拒）→
   回退 `created` + 502，调用方可用同一个键安全重试。
4. **webhook 验签 + 防重放 + 幂等 + 乱序**：用原始字节做 HMAC-SHA256 常量时间比较；
   `|now - t| > 300s` 拒绝（`X-Bench-Now` 可覆盖 `now`）；按事件 id 去重；退款事件按 `refund_id` 记账；
   先到的退款通知暂存，订单变为 `paid` 后自动补应用。
5. **金额以订单为准**：webhook 的金额和订单不符 → `payment_review`，`paid_cents` 不增加，绝不静默计为已收。
6. **退款预留**：可退额 = `paid_cents - refunded_cents - 进行中的退款预留`；退款结果不确定时保留预留，
   用同一个键重试才安全；网关侧累计退款上限是最后一道防线。
7. **对账**：`POST /api/admin/reconcile` 对所有 `payment_pending`/`payment_unknown` 订单查网关收敛，
   顺带补应用乱序事件，返回 `{"checked": n, "updated": n}`。

关键抉择、有意没做的事、已知风险都写在 `DECISIONS.md`；行为规范（错误码、边界、各故障下的期望）
写在 `SPEC.md`。

## 我实际验证了什么（都是真实跑出来的数字）

### 1. 契约测试套件：42 个用例，42 PASS / 0 FAIL（约 34s）
黑盒：只通过 HTTP 和网关 `/__ctl/*` 交互，不 import 被测实现。覆盖订单 CRUD/校验、pay 幂等（同键并发 ×5、
双击、跨订单冲突）、已支付/进行中拒绝、网关 5xx/429/timeout/drop、webhook 验签/原始字节/防重放/±300s 边界/
X-Bench-Now、重复与未知事件、金额不符→`payment_review`、退款部分/全额/超退/并发防超卖/网关故障同键重试、
乱序退款、重复退款事件、reconcile 收敛。

### 2. 测试套件对“错误实现”的检出能力：8/8 变异体被抓住
`tools/mutants/` 在不改任何源码的前提下 monkey-patch 出 8 类常见支付对接错误，
每个变异体都能被至少 1 个用例判 FAIL（矩阵见 `tools/mutants/REPORT.md`）：
`no_sig`（不验签）、`no_stale`（不校验时间戳窗口）、`no_dedupe`（重复事件重复计退款）、
`trust_amount`（信任 webhook 金额）、`no_idem`（pay 无幂等 + 网关幂等键随机）、
`refund_no_idem`（退款无幂等）、`no_ooo`（丢弃乱序退款事件）、`reconcile_noop`（对账不收敛）。

### 3. 故障矩阵探针：17 个场景 / 300 条断言，17/17 PASS（两次以上连跑）
每类故障都用网关 `/__ctl/state` 的真实数据证明，而不是只看接口返回：
- `charges_create` 的 http500/rate_limit/timeout/drop_after：`charge_created <= 1`，最终 paid 有网关 succeeded 扣款背书；
- `refunds_create` 的 http500/timeout/drop_after：首次 502，同键重试 200，网关 **恰好 1 笔**退款、金额正确、`refunded <= paid`；
- webhook duplicate（不翻倍）、hold+reverse（退款通知先到最终落账）、off（靠 reconcile 收敛）；
- 并发：同键 pay ×10（全部 202 且响应体一致、只扣 1 笔）、不同键 pay ×5（1×202 + 4×409、只扣 1 笔）、
  并发退款 3×3000（合计 9000 == refunded <= paid）、超额退款 409 且网关没有多出来的退款；
- 金额不符 webhook → `payment_review`、`paid_cents=0`、且没有调用网关扣款。

### 4. 我另外做的验证
- **全局对账压测**：20 单并发混合支付+部分/全额退款+重复点击，结束后
  `Σ order.paid_cents == Σ 网关成功扣款金额 == 31396`、`Σ order.refunded_cents == Σ 网关退款金额 == 13539`、
  `charge_created=20`（每单恰好 1 笔）、无越界（`paid<=amount`、`refunded<=paid`）。
- **崩溃恢复**：在 pay 请求卡在网关时 `kill -9` 服务 → 重启后该订单为 `payment_unknown` →
  `reconcile` 收敛为 `paid`，网关恰好 1 笔扣款；用同一个键再次 pay 得到 409 `ALREADY_PAID`，没有第二笔。
- **真乱序**：用 `webhook_mode=hold` 把 `charge.succeeded` 扣住，直接向网关发起退款，再 `flush reverse`
  让 `refund.succeeded` 先到 → 订单最终 `refunded_cents=900`、`status=refunded`（事件没有丢）。
- **Windows 落盘抖动**：`os.replace` 在 Windows 上偶发 `WinError 5`，`save()` 做了有限重试 + 兜底写，
  避免把落盘抖动变成业务 500（这是自检时真实踩到并修掉的）。

## 没做 / 不确定 / 已知边界

- **没有图形界面**：题目交付的是 HTTP 服务，验证通过测试套件与探针完成；没有为了“能点”而搭 UI。
- **单进程 JSON 快照存储**：适合本任务规模；生产要换 SQLite/Postgres 并做跨进程并发控制。
  事件表不清理、全量重写，订单量大时会写放大。
- **退款“不确定”的收敛依赖外部**：网关没有“按 charge 查退款”的接口。退款超时后只有两种收敛路径：
  调用方用同一个 `Idempotency-Key` 重试（网关幂等重放），或 `refund.succeeded` webhook 到达。
  两者都没有时，金额预留会一直占着（这是“不猜”的代价，宁愿挡住新退款也不冒多退风险）。
- **重复扣款不自动退**：同一订单出现第二笔成功扣款时标 `payment_review`，交给人工（自动退款要先判断退哪一笔，错判代价更高）。
- **没有后台定时对账**：有意为之，避免评测中间状态被后台线程改写；收敛只有 webhook 和显式 `POST /api/admin/reconcile` 两条路径。
- **`payment_review` 不会自动解除**：金额不符必须人工介入，这与“不猜”一致。
- **`bench.json` 的命令假定 cwd 是 `paydesk/`**（脚本内部不依赖 cwd）；解释器用 `python3 || python` 兼容 Linux/Windows。
- **几处契约没规定、由我定的行为**（都写在 `SPEC.md`）：`GET /api/orders?status=` 返回 JSON 数组、
  方法不对返回 405 `METHOD_NOT_ALLOWED`、`/api/health` 是扩展、`IDEMPOTENCY_CONFLICT` 是自定义错误码、
  `sku` 纯空白视为非法、pay 遇网关明确失败返回 502。
