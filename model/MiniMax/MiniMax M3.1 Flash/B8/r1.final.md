# FINAL_MESSAGE —— paydesk（对接 PayGate 支付网关的商户后端）

## 一、做了什么

在 `paydesk/` 里实现了一个**只用 Python 标准库**（`http.server` + `sqlite3` + `hmac` + `urllib`）的商户后端，
对接题目提供的 PayGate 沙箱。契约里的接口全部实现：

| 接口 | 状态 |
|---|---|
| `POST /api/orders` | ✅ 201 + 订单；`sku` 1–64 字符、`amount_cents` 1–10000000 整数校验，否则 400 `VALIDATION_ERROR` |
| `GET /api/orders/{id}` / `GET /api/orders?status=` | ✅ 订单对象 / JSON 数组；不存在 404 `NOT_FOUND` |
| `POST /api/orders/{id}/pay` | ✅ 缺 `Idempotency-Key` → 400 `IDEMPOTENCY_KEY_REQUIRED`；202 + 订单；同键同结果；已支付 409 `ALREADY_PAID`；支付中/待核对 409 `PAYMENT_IN_PROGRESS`；失败后可用新键重付；20 秒内必回 |
| `POST /api/webhooks/pay` | ✅ 原始字节 HMAC 验签（常量时间）→ 400 `INVALID_SIGNATURE`；超窗 → 400 `STALE_TIMESTAMP`；重复事件/未知订单 → 200 |
| `POST /api/orders/{id}/refund` | ✅ 缺键 400；未支付 409 `NOT_REFUNDABLE`；超额 409 `REFUND_EXCEEDS`；网关不可用 502 `PROVIDER_UNAVAILABLE`（同键重试安全）；成功 200 + 订单 |
| `POST /api/admin/reconcile` | ✅ `{"checked": n, "updated": n}` |
| `POST /api/__bench/reset` | ✅ 只清自己的数据（不碰网关） |
| `X-Bench-Now` | ✅ 存在时作为 webhook 时间戳窗口的"当前时间" |

外加一个零依赖的收款台页面（<http://127.0.0.1:8080/>），可以建单、支付、退款、对账，实时看订单状态。

### 钱是怎么保证的（核心思路）

1. **金额只从事实表 `SUM` 出来**，绝不"在旧值上加" —— 重复通知 / 乱序通知在数学上不可能把金额算多。
2. **订单状态是唯一派生物**：所有写路径最后统一 `recompute`，所以"webhook 先到、接口响应后到"不会互相覆盖。
3. **网关幂等键 = 订单 + 尝试序号 + 随机后缀**：同一次尝试的重试复用同一个键（只扣一次），
   不同尝试必然不同键（评测重置后也不会回放旧扣款）。
4. **订单 id 永不复用**（bench reset 不复位自增序列），避免在途旧 webhook 按 `reference` 撞到新订单。
5. **退款先"占额度"再打网关**：网关抽风时预留不释放，防止用别的键再退一次导致多退。
6. **拿不准就说不确定**：结果不明 → `payment_unknown`；金额不符 → `payment_review`（且不认这笔钱、不允许自动退）。

## 二、怎么跑

```bash
# 网关沙箱
cd provider-sim && PORT=9100 PROVIDER_KEY=sk_test_bench WEBHOOK_SECRET=whsec_bench python provider.py

# 商户后端（bench.json 的 start 命令就是它）
cd paydesk && PORT=8080 DB_PATH=./paydesk.db PROVIDER_URL=http://127.0.0.1:9100 \
  PROVIDER_KEY=sk_test_bench WEBHOOK_SECRET=whsec_bench BENCH_MODE=1 python server.py

# 健康检查 / 测试
python healthcheck.py
BASE_URL=http://127.0.0.1:8080 PROVIDER_URL=http://127.0.0.1:9100 python run_tests.py
```

`paydesk/bench.json` 的四条命令（`start` / `setup` / `test` / `health`）我都**逐字跑过**，退出码都是 0；
`setup` 是空依赖清单（`pip install -r requirements.txt` 必然成功）。工作目录根部另放了 `server.py` /
`run_tests.py` / `healthcheck.py` 三个薄壳，所以评测方把工作目录设成 `paydesk/` 或工作目录根部都能跑。

## 三、怎么验证的（都真跑过）

* **完整用例**：`45 passed`（`paydesk/tests/`，5 个文件），全程对着真实沙箱跑，约 21 秒。
* **逐类故障复现**（用沙箱注入，断言的是网关侧真实扣款次数/金额，不是接口返回了什么）：
  - `drop_after`（连接被掐断）：`charge_created` 只 +1，订单最终 `paid`；
  - `timeout`（网关把响应压住 30 秒）：**8.2 秒**返回 202（契约要求 20 秒内），只扣一次；
  - `http500` × 3：服务自己退避重试，只扣一次；
  - `duplicate` 通知模式：`paid_cents` 恰好等于订单金额（没有翻倍）；
  - `hold` + 倒序 `flush`：退款通知先于扣款通知到达，**退款最终正确体现在订单里**；
  - `webhook_mode=off`（通知全丢）：订单停在 `payment_pending`，`POST /api/admin/reconcile` 后收敛为 `paid`；
  - 网关整体挂掉：15 秒内返回 502，订单标成 `payment_unknown`（不假装成功）；网关恢复后**用同一个键重试**，
    `charge_created` 仍然只 +1。
* **"通知比响应先到"**：用 `timeout hold_s=3` 制造，webhook 先落地，接口响应没有把状态改回 `payment_pending`。
* **并发狂点**：6 个线程同时打同一个键 → 6 个 202，`charge_created` 只 +1。
* **浏览器实测**：用真实浏览器点了一遍收款台（建单 → 支付 → 状态变"已支付" → 对账），无 console 报错。
* **测试有效性对照**：我另写了一个**故意写错**的实现（不幂等、金额累加、按 seq 丢弃乱序事件、不验签、
  退款不校验额度、网关 500 就放弃），拿本仓库的测试跑它 → **45 个用例里 22 个失败**，
  失败点正好落在这些典型错误上。验证完已删除该文件。

## 四、过程中真正抓到的两个 bug（已修，并补了回归用例）

1. **网关幂等键撞车**：早期用 `pa_{订单号}_{序号}`，而 `/api/__bench/reset` 只清我们自己的数据、不清网关；
   评测重置后订单号从 1 重新开始 → 网关回放了一笔**旧的、金额不同**的扣款。
   修法：幂等键加随机后缀（同一尝试重试仍复用同一个键）。
2. **订单 id 复用导致旧 webhook 撞新订单**：一笔在途的旧退款通知按 `reference` 落到了新订单上，
   让新订单凭空多出 `refunded_cents`。修法：reset 不复位自增序列，id 永不复用。

另外顺手修了收款台定时刷新重建 DOM 导致按钮点不中的问题（数据没变就不动 DOM）。

## 五、没做 / 不确定的地方

* **没有鉴权/多租户/限流**：契约没要求，凭空加一层可能反而挡住评测调用。
* **没有自动对账定时任务**：只提供 `POST /api/admin/reconcile` 触发式对账，没起后台定时器。
* **单进程部署**：SQLite + 进程内锁，多副本要换存储层。
* **`payment_review` 的订单不允许退款**（金额不符时不知道该退多少），需要人工介入 —— 这是刻意的。
* **`GET /api/orders` 返回裸 JSON 数组**：契约唯一没有硬性规定返回形状的地方，我按"单个订单返回裸对象"
  的一致性选的；若评测方期望 `{"orders": [...]}` / `{"data": [...]}`，改 `service.list_orders` 的包装即可。
* **8 秒 socket 超时**是拍的：网关单次处理超过 8 秒时我们靠"同键重试"兜底（安全，但响应会推后到 ~8 秒多）。
* 测试里有几处依赖沙箱的 `/__ctl/*`（故障注入、读真实扣款次数）——那是题目提供的沙箱能力，对着真实网关没有意义。
* 工作目录里只剩几个空目录（`.pytest_cache` / `__pycache__` / `.selftest`）：本机的删除通道拒绝对该路径下的
  **目录**做回收站删除，文件都已清空，这些目录里已经没有内容。
