# FINAL_MESSAGE — B2 账务与转账服务

## 交付内容

`ledger/` 目录：

| 文件 | 说明 |
|---|---|
| `server.py` | HTTP 层：路由、参数校验、幂等包装、错误格式（Python 标准库，`http.server`） |
| `store.py` | SQLite 存储层：schema、事务、业务操作、幂等表 |
| `tests/test_api.py` | 黑盒测试套件，127 项断言，只读 `BASE_URL`，不自起服务 |
| `tests/crash_check.py` | 崩溃耐久性自检：自起服务、打流量、`kill -9`、重启校验 |
| `bench.json` | `start: python3 server.py`，`setup: ""`，`test: python3 tests/test_api.py`，`health: /health` |
| `README.md` / `DECISIONS.md` | 使用文档 / 设计决策与规格歧义处理 |

零第三方依赖，无 lock 文件（纯标准库）。

## 关键设计

- **持久化**：SQLite 单文件，`journal_mode=WAL` + `synchronous=FULL`；余额、
  流水、幂等记录写在同一个 `BEGIN IMMEDIATE … COMMIT` 里，**COMMIT（fsync）
  完成后才发送 HTTP 响应**。
- **并发**：单连接 + 进程级锁把每个请求串行化——并发扣款不会透支、并发同
  key 幂等只生效一次、并发冲正只成功一次，这些都是“检查+写入在同一临界区”
  的直接推论。
- **幂等**：指纹 = `METHOD + path + 规范化JSON`（排序键，字段顺序无关）；
  命中同请求→回放原状态码+原文 body+`Idempotent-Replay: true`，命中不同
  请求→409 `IDEMPOTENCY_MISMATCH`；只有 2xx 占 key；key 检查先于一切。
- **检查顺序**：幂等 key → JSON 解析 → 幂等查找 → 字段校验(400) → 存在性
  (404) → 业务(422/409)；`SAME_ACCOUNT` 在存在性之前（纯输入属性）。

## 验证方式

- `tests/test_api.py`：127 项断言全过。覆盖全部接口与错误码、边界值
  （amount=1/1e9、key=64、owner=40、memo=100）、幂等回放/冲突/失败不占 key、
  跨接口共用 key 空间、冲正全部错误路径、分页游标、不变量（流水和=余额、
  total==deposits）、并发（10 并发冲正仅 1 成功、10 并发同 key 入账只生效
  一次、20 并发转账抽干账户不透支）。
- `tests/crash_check.py`：往账户连打 300 笔入账，`kill -9`（Windows 上等价
  强制终止），同 `DB_PATH` 重启后：已应答的 300 笔全部在账、流水一一对应、
  seq 严格递增无重复、崩溃前的幂等 key 重放仍返回原响应并带 replay 头。
- 手动验证：HEAD `/health`、`BENCH_MODE` 关闭时 reset 404、`DB_PATH` 父目录
  自动创建、冲正流水方向（reversal_out/reversal_in）与 ref 正确。

## 已知限制

- 串行写入是刻意的正确性取舍；读也走同一把锁，吞吐上限约等于单次 fsync
  延迟（数百~上千 ops/s），对本题规模足够。
- SQLite INTEGER 上限 ~9.2e18 分，理论溢出未防护（溢出→500，实际够不到）。
- 严格模式：请求带未知字段 → 400；`memo:null` 视为未提供；详见 DECISIONS.md。
