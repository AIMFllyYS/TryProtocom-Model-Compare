# B7 第 1 次运行 — FINAL_MESSAGE

## 做了什么

`reportdesk/` 是标准库 + SQLite 的内部报表服务，"功能正确但慢"。慢的根源不在 SQL 本身，而是**每个请求都在 Python 里做全表线性扫描 + 逐单查明细**：

- `all_orders()` 每请求拉全部 2 万行；`top-products` 再对 ~1.85 万个已付款订单各发一次 `items_of` ——单请求上万次查询；
- 全局 `LOCK` 把整个路由串行化，单请求 20–200ms → 8 个并发就排队（实测最重端点 p50 ≈ 951ms）。

改动全部在 `app.py`（没有重写，没有引入第三方依赖）：

1. 聚合/过滤下沉为 SQL：`top_products` / `monthly` / `customer_summary` 改 `JOIN + GROUP BY + 聚合`；`list_orders` 用 `WHERE + ORDER BY created_at DESC, id DESC + LIMIT/OFFSET`；`get_order`、`create_order` 的 max(id)、客户/商品存在性改主键直查。
2. 列表页明细用一条 `order_id IN (...)` 批量取回归组，消除 N+1。
3. 新增 5 个索引（含 `order_items(order_id,…)` 覆盖索引），`load_seed` 建、启动时 `IF NOT EXISTS` 兜底、`ANALYZE` 更新统计。
4. `create_order` 包进 `BEGIN/COMMIT`（失败回滚），消除半成品订单窗口。

**没加缓存、没建物化表、没放开全局锁**——写一提交下一次读立刻可见，理由写在 `PERF-REPORT.md`（含 10x 数据、多实例/重启的边界分析）。

## 结果（实测，方法见 PERF-REPORT.md）

- 单请求中位数：`top-products` 全区间 197→43ms，`monthly` 47→7ms，客户汇总 ~30→2ms，订单列表 ~40→3ms。
- 并发（8 线程）：最重端点吞吐 8.3→35 req/s、p50 951→221ms；monthly 292 req/s；orders 396 req/s。

## 怎么验证的

- 优化前先把 14 个代表性端点的完整响应存成快照，改完 `tools/measure.py compare` **逐字段一致**（状态码 + JSON 全体）。
- `python -m pytest -q tests`：27 个用例全过。golden 数字（月度/客户汇总/排行榜/总数）来自种子数据的确定性真值；另有写后立读、取消联动、改价只影响新单、created_at 并列时 id 倒序、分页一致性、16 线程并发下单不丢单不重号、reset 还原、错误码/错误体格式等。
- 冒烟：全新 DB 冷启动 → `compare` 一致 → 测试全过。

## 没做/不确定

- `top-products` 全区间仍要扫区间内全部明细，10x 数据下预计 ~0.4–0.5s；要做更快得上"按天×商品"汇总表并在写路径同步维护——本次权衡后没做（见报告）。
- 全局 `LOCK` 保留：多实例共库写入时 `max(id)+1` 可能撞主键（与原实现相同的既有边界，单实例无影响）。
- 测试断言的 golden 数字依赖种子数据本身确定；`X-Bench-Now` 与 reset 行为保持不变。
