- `server.js` — 全部业务：订单 CRUD、`/pay`（幂等发起扣款）、`/webhooks/pay`（验签 + 事件应用）、`/refund`（幂等退款）、`/admin/reconcile`、`/__bench/reset`、`/health`

- `tests/run-tests.js` — 28 项集成测试（对运行中的服务 + 沙箱，断言会核对 `/__ctl/state` 的真实扣款数/退款额，而不是只看接口返回）
- `README.md` / `DECISIONS.md` / `package.json`

环境变量全部按契约：`PORT`、`DB_PATH`、`PROVIDER_URL`、`PROVIDER_KEY`、`WEBHOOK_SECRET`、`BENCH_MODE`。

## 怎么验证的

沙箱 `provider.py`（:9100）+ 本服务（:8201）本地实跑：

- `tests/run-tests.js`：**28/28 通过**（连跑两次，中途修掉两处真实 bug 后全绿）。
- 每类注入故障都复现过：`drop_after`（响应丢了但已扣款→按 reference 反查收养）、`timeout`（hold_s=2 和 hold_s=15 两档，10.3s 响应 < 20s）、`http500`、`rate_limit`、`webhook_mode=off/hold/duplicate`。
- 关键金额证明：`counters.charge_created` 恒为 1（并发同键/异键、drop、重放均不产生第二笔扣款）；refund drop_after 后同键重试 → provider 侧 `refunds.length === 1`。
- 乱序：hold 住 charge.succeeded，先投递 refund.succeeded → 订单落在 `refunded`，事件不丢。
- 手动补充验证：provider 整体宕机 → `payment_unknown`（0.38s 响应）；恢复后 reconcile → `created`（确实没扣款）→ 新键重新支付成功；进程重启后订单与幂等结果保持（含注入 pending 记录模拟崩溃中途 → 同键重试复用 `pay-<order>-<n>` provider key，网关幂等重放，不产生第二笔）；签名错/过期/`X-Bench-Now` 平移窗口均按预期。

## 核心设计（详见 DECISIONS.md）

- **不确定就用网关查真相**：create 失败分不清"已处理丢响应"还是"未处理"时，一律 `GET /v1/charges?reference=` 反查；查不到才可安全重试一次；查不到且网关也挂了 → `payment_unknown`，交给 reconcile 收敛。
- **状态是推导出来的**：订单 status 由（扣款结果，Σ退款）重算，乱序/重复的退款事件天然收敛；`refund_id` + `event.id` 双重去重。
- **幂等键分层**：客户端键存结果快照（完成态）；尝试级 provider key 在调用前落盘，崩溃恢复重试走网关幂等重放；退款瞬时失败返回 502 且不消费键 → 同键重试安全。
- **pending 快照不降级已知终态**：webhook 先于 create 响应到达时不会被回写覆盖。

## 没做 / 已知限制

- `payment_review`（金额不符）不自动解除、不可退款、不可重付 —— 留给人工；reconcile 也不会清这个标记。
- 网关没有"列退款"接口，退款真实额只能通过响应或 webhook 得知；`drop_after` 场景靠"同 provider key 重试 → 重放"闭环，测试已证明不会多退。
- 单进程设计，`DB_PATH` 不支持多写者；Windows 下 rename 偶发 EPERM 已加重试兜底。
- 事件去重集合随事件量增长（bench 规模无碍）。

## 最值得看的地方

`executePay` 的反查逻辑（server.js `executePay`）+ `recompute` 派生状态机 —— 这两处是"不多扣、不少收"的落点；`refund` 的"502 不消费键 + 稳定 provider key"是"不多退"的落点。
