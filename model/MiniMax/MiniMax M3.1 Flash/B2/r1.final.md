# FINAL_MESSAGE —— 账务与转账服务

## 交付了什么

`ledger/` 目录，一个**零第三方依赖**的 Node.js 账务服务（只要 Node 22+）：

```
ledger/
├─ bench.json            启动 / setup / 测试 / health 约定
├─ package.json          零依赖，engines: node >= 22
├─ package-lock.json     锁文件（依赖集为空）
├─ README.md             启动、接口、配置、并发与持久化保证、怎么跑测试
├─ DECISIONS.md          规格没写清楚的地方，我的取舍与理由（30+ 条）
├─ src/
│  ├─ server.js          启动入口（PORT / DB_PATH / BENCH_MODE）
│  ├─ http.js            路由、请求体解析、错误映射、幂等键校验
│  ├─ ledger.js          领域模型 + 业务规则 + 落盘编排（单写者队列）
│  └─ journal.js         追加式 WAL：append + fsync，启动时重放
├─ test/
│  ├─ run-tests.js       自检套件（370 条断言，打 BASE_URL，不自己起服务）
│  ├─ persistence-check.js   kill -9 持久化验证
│  ├─ chaos-check.js         请求进行中被杀的不变量验证
│  ├─ smoke.js / *.ps1       手动冒烟与本地辅助脚本
└─ verify-artifacts/     本地验证留下的运行时文件（NOTES.md 里有逐个说明）
```

一条命令启动：

```bash
cd ledger && PORT=8080 DB_PATH=/tmp/ledger.log BENCH_MODE=1 node src/server.js
```

`bench.json` 里的 `start` / `test` 写成了对工作目录不敏感的形态
（`sh -c 'if [ -d ledger ]; then cd ledger; fi; exec node src/server.js'`），
在 `ledger/` 里跑或在上一层目录跑都行；`setup` 是空的（不需要装任何依赖）。

## 怎么验证的

我自己在 Windows 开发机上完整跑过下面这些（脚本都在 `ledger/test/` 里，可以复跑）：

1. **功能自检**：`BASE_URL=… node test/run-tests.js` → **370 条断言全过**。
   覆盖金额边界（0/负数/小数/字符串/布尔/null/超上限/1e9）、幂等重放与冲突、
   4xx 不占 key、转账/冲正的全部错误码与检查顺序、流水分页、汇总、
   并发（20 笔并发扣款恰好 10 成功、同 key 并发只生效一次、同笔转账并发冲正只成功一次）、
   错误不泄露堆栈、流水之和恒等于余额。

2. **kill -9 持久化**：建账户 → 入账 → 转账 → `SIGKILL` → 用同一个 `DB_PATH` 重启，
   校验账户、余额、对手方余额、转账对象、流水、汇总、以及**幂等记录仍在**
   （重放同一个 key 仍返回第一次的响应体，且带 `Idempotent-Replay: true`）。
   → `test/persistence-check.js`，12 项全过。

3. **日志尾部撕裂**：手工往 WAL 追加一行写了一半的 JSON，重启后服务正常起来，
   撕裂的那行被丢弃，之前的状态一条不少。

4. **请求进行中被杀（混沌测试）**：压测跑到一半 `SIGKILL` 掉服务
   （客户端拿到 666 个 2xx，19334 个请求在途中被掐断），用同一个 `DB_PATH` 重启后校验：
   **客户端收到过 2xx 的每一笔转账都还在且仍是 `posted`**、两个账户余额都不为负、
   流水金额之和 == 账户余额、A+B 之和守恒、`total_cents == deposits_cents`。→ 全过。

5. **端到端彩排**（`test/rehearsal.ps1`，就是评测会做的事）：
   全新 `DB_PATH` 启动 → 跑自检套件（370 过）→ `SIGKILL` → 同 `DB_PATH` 重启
   → 再跑一遍自检套件（370 过）。**说明测试套件本身是状态无关的**，
   评测在重启后重跑它也不会误报。

6. **写延迟基准**（`test/bench.ps1`）：100 次串行写 119ms、200 次并发写 202ms
   ——约 1.2ms/次写（含 fsync）。

## 最想让你看的地方

1. **`src/ledger.js` 的 `mutate()`**——所有写操作都走同一条串行队列，
   "规划 → 落盘 → 应用内存"三步是分开的。转账的原子性、幂等的 exactly-once、
   余额永不为负，全部是这一个设计推出来的，没有额外的锁或事务代码。

2. **`src/journal.js` 的 `append()`**——`write()` + `fsync()` 之后才返回，
   也就是说"凡是返回过 2xx 的操作一定在盘上"。重启时按顺序重放，
   尾部半行按"未提交"丢弃。

3. **`test/run-tests.js`**——它只打一个已经在跑的服务，全程只用相对量
   （增量 / 本次创建的账户），所以在"全新库"和"复用旧库"下都能跑；
   拿它去跑"故意改错"的实现，余额变负、幂等重放不幂等、冲正不回滚、
   错误码错位、并发超扣这些都会被逮住。

4. **`DECISIONS.md`**——规格留白的地方我都写了取舍和理由，
   比如 `SAME_ACCOUNT` 与 `NOT_FOUND` 谁优先、`ALREADY_REVERSED` 与
   `INSUFFICIENT_FUNDS` 谁优先、幂等指纹到底算哪些字段、
   `memo` 缺省返回 `null` 还是省略、流水对象是否带 `account` 字段
   （我选择严格按规格给的字段集，不多加字段）。

## 已知限制 / 没做的事

* **单进程单写者**，吞吐约 800 写/秒。要更高得换成 SQLite 或分片日志，接口不用动。
* **WAL 只增不减**，没有做快照/归档/压缩。长时间运行文件会一直变大。
* **只做了 exactly-once 副作用**，没有做 exactly-once 投递：
  客户端超时重试必须带同一个 `Idempotency-Key`，服务端保证同 key 同请求只生效一次；
  同 key 不同请求返回 409，不会"帮客户端猜"。
* **没有建模操作者/时间戳/币种/手续费/对账导出**，规格没要求，也没自作主张加。
* `ledger/verify-artifacts/` 是本地验证留下的运行时文件（WAL 快照、状态文件），
  评测时用 `DB_PATH` 指向新路径即可，不会被读到。
  说明：本沙箱的可恢复删除只覆盖 session workspace，交付目录在它之外，
  所以我没能删掉这些产物，改为整理成带说明的证据目录。
* `.ps1` 辅助脚本是 Windows 用的；评测机是 Linux 的话用不到（`bench.json` 里只有
  `node` 命令）。另外提醒一句：Windows PowerShell 5.1 会把无 BOM 的 UTF-8 `.ps1`
  按 ANSI 解码，中文注释会变成乱码并可能把后面的语句吃掉——所以那几个 `.ps1`
  我都写成了纯 ASCII。
* `test/run-tests.js` 里有一条"数据文件存在且非空"的检查，只在环境变量 `DB_PATH`
  存在时启用，否则跳过（评测若不给测试进程传 `DB_PATH` 就不做这项断言）。
