# FINAL_MESSAGE — 带租约的作业队列

## 交付了什么

`job-queue/` 是一个**零依赖**（Python 3.11+ 标准库）的 at-least-once 作业队列服务，
SQLite 持久化、租约原子领取、惰性过期、请求级时钟（`X-Bench-Now`）、`kill -9`
后可原样重启。

| 文件 | 作用 |
|---|---|
| `job-queue/bench.json` | 启动/安装/测试/健康检查约定（`setup` 为空：无需安装） |
| `job-queue/server.py` | 入口：解析 `PORT` / `DB_PATH` / `BENCH_MODE`，启动 HTTP 服务 |
| `job-queue/jobqueue/store.py` | SQLite schema、事务边界、惰性租约过期、排序、死信顺序 |
| `job-queue/jobqueue/httpapi.py` | 路由、JSON 响应、统一错误信封、方法/协议兜底 |
| `job-queue/jobqueue/validation.py` | 全部请求参数校验（统一 400 `VALIDATION_ERROR`） |
| `job-queue/jobqueue/timeutil.py` | UTC 毫秒时间解析/格式化 |
| `job-queue/tests/run_tests.py` | 评测用的黑盒测试套件（读 `BASE_URL`，不自己起服务） |
| `job-queue/README.md` | 启动、接口、配置、行为 |
| `job-queue/DECISIONS.md` | 规格未明说处的决策与理由 |
| `job-queue/tools/*.py` | 我额外做的验证工具（spec 对照、kill -9 持久化、变异测试、冒烟） |

**运行方式**（`bench.json` 里的命令相同，且已实测在 `cwd=job-queue` 与 `cwd=工作目录`
两种情况下都能用）：

```sh
cd job-queue
PORT=8080 DB_PATH=/tmp/jobs.db BENCH_MODE=1 python3 server.py
# 另一个终端：
BASE_URL=http://127.0.0.1:8080 BENCH_MODE=1 python3 tests/run_tests.py
```

没有依赖清单/lock 文件的需求（纯标准库），`setup` 留空。

## 关键设计（详见 DECISIONS.md）

- **先落盘再响应**：每个请求是一个 `BEGIN IMMEDIATE … COMMIT` 事务；SQLite 用
  WAL + `synchronous=FULL`，提交（含 fsync）完成后才写响应。进程被 `kill -9`
  只会留下完整事务或没有事务，重启无需回放业务日志。
- **领取原子性**：进程内一把可重入锁 + SQLite 写事务串行化，两个 worker（线程或
  共享同一 `DB_PATH` 的两个进程）不可能拿到同一作业。已实测：60 个作业 × 2 个
  服务进程 × 8 个并发线程，全部恰好各被领取一次。
- **惰性时钟**：没有后台定时器。每个请求先按该请求的 `now` 结清所有到期租约
  （所有队列），所以任何接口看到的状态一致；租约过期后 `run_at` 取**租约到期时刻**
  （而不是发现时刻），恢复的作业保持原有排队位置。
- **令牌语义**：保留“最近一次租约令牌 + 到期时刻 + 是否已确认/失败”，据此区分
  `LEASE_MISMATCH` / `ALREADY_FINISHED` / `LEASE_EXPIRED`；requeue 清除令牌，
  旧令牌一律 mismatch。
- **顺序与退避**：`priority DESC, run_at ASC, seq ASC`；nack 退避
  `min(1000×2^(attempts−1), 60000)`；死信按进入死信的先后（持久化单调序号）排序。
- **无 500**：预期错误走统一错误信封；意外异常只在服务端 stderr 记录，对客户端
  返回通用 400，绝不泄露堆栈。

## 怎么验证的（全部是真实跑过的结果）

1. **评测用黑盒套件** `tests/run_tests.py`：最终版本 **703 条检查全部通过**
   （约 5.7–7.4s），并在同一个实例上连续跑两遍仍然全绿（证明随机队列名隔离，
   不依赖 reset/空库）。它是唯一的 `bench.json` test 目标，纯 HTTP、不创建文件、
   不启停服务。
2. **独立 spec 对照** `tools/spec_check.py`（另一位协作者按契约独立编写，未复用
   上面套件）：**309 条检查，309 通过，0 失败**。
3. **持久化/崩溃** `tools/durability_check.py`：**71/71 通过**。覆盖排队、租约、
   ack、nack、delayed、dead、requeue 在 `kill -9` + 同 `DB_PATH` 重启后的状态；
   请求洪流中硬杀后 `PRAGMA integrity_check=ok`、状态机与 `attempts` 一致；
   已返回 200/201 的变更（enqueue/ack/nack/requeue/reset）在立即硬杀后仍可见。
4. **变异测试** `tools/mutation_check.py`：向服务副本注入 **24 个真实规格违反**
   （优先级倒序、run_at tiebreak 反序、插入序反序、租约不涨 attempts、重复领取、
   过期边界用严格大于、过期把 run_at 写成 now、死信阈值差一、任意令牌可 ack、
   重复 ack 返回 200、退避指数/上限错、默认死信原因错、requeue 不清 attempts/
   last_error、stats 交换 ready/delayed、死信顺序用插入序、租约字段改名、忽略
   X-Bench-Now、队列名允许大写、delay 不加进 run_at、nack 忽略 retry_delay_ms、
   requeue 非死信、404 换 400）。结果：baseline 全绿（703 checks），
   **24/24 全部被测试套件抓出**（套件哈希在矩阵前后一致）。
5. **命令与可移植性**：用 `bench.json` 的 start/test 命令实测 `cwd=job-queue` 与
   `cwd=工作目录` 两种启动方式均可用；所有 14 个 Python 文件通过
   `ast.parse(..., feature_version=(3, 11))`；本机在 Python 3.14 上开发验证，
   代码只用 3.11 已有标准库接口。
6. 我另外用脚本逐项点过：路由/方法/404/405、非法 JSON、超大 body（1 MiB 上限）、
   chunked 拒绝、健康检查、`BENCH_MODE` 关闭时 reset 为 404、reset 204 且清空全部
   状态、时间格式（`Z`/偏移/日期）与非法 `X-Bench-Now`、多进程共享 DB 原子领取、
   `kill -9` 后 ack 不丢、租约跨重启仍有效并在到期时刻恢复。

## 已知限制 / 需要知道的取舍

- **at-least-once**：提交成功但响应未送达时客户端重试可能重复处理，worker 应幂等。
- 单机 SQLite 存储；多个服务进程共享一个 `DB_PATH` 是安全的（SQLite 写锁 +
  busy_timeout），但不是分布式队列。
- 请求体上限 1 MiB；`Transfer-Encoding: chunked` 不支持（评测客户端用
  Content-Length）；无鉴权/TLS/Web UI；只实现规格接口 + bench reset，没有额外的
  列表/删除接口。
- `X-Bench-Now` 非单调（时间倒流）不做补偿：已经发生的状态迁移（租约恢复、死信）
  不会被“撤销”；正常单调时钟下无影响。
- 规格留白处的选择都写在 `DECISIONS.md`，其中较可能被问到的几条：
  缺失/空 `lease_token` → `409 LEASE_MISMATCH`（规格把“没带令牌”归入 mismatch）；
  `extend` 的 `lease_ms` 必须为 1000–600000 整数；不存在的队列 `stats/dead` 返回
  200 全零/空列表；`/health` 对非法 `X-Bench-Now` 仍返回 200（但非 GET/HEAD 为 405）。
- `tools/` 下四个脚本是开发期自检工具，不是评测 test 命令的一部分；它们会启动
  临时进程/写 `tests/_tmp/`，交付前已清理，最终目录里没有临时文件、数据库或缓存。
