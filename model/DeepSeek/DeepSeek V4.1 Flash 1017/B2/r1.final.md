# FINAL MESSAGE

## What was delivered

`ledger/` — a small, durable internal accounting service written in **Python
3.11+ standard library only** (no third-party dependencies, so `setup` is empty
and no lock file is needed) with SQLite as the storage engine.

| File | Role |
|---|---|
| `server.py` | entry point: env config, signal handling, HTTP server |
| `api.py` | HTTP routing, request parsing/validation, JSON errors, protocol hardening |
| `service.py` | business rules, idempotency, single global serialisation lock |
| `store.py` | SQLite schema and transactional persistence (WAL + `synchronous=FULL`) |
| `jsonutil.py` | deterministic JSON (byte-identical replays, canonical fingerprints) |
| `bench.json` | start / setup / test / health contract |
| `tests/run_tests.py` | black-box conformance suite against a live `BASE_URL` (the bench `test` command) |
| `tools/durability_check.py` | separate kill -9 / chaos durability harness |
| `README.md` | start-up, configuration, API, error model, design summary |
| `DECISIONS.md` | every point where the spec was silent/ambiguous and the choice made |

Everything required by the contract is implemented: accounts, deposits,
transfers, reversals, entries with global `seq`, pagination, bank summary,
persistent idempotency, bench reset, `/health`, `PORT` / `DB_PATH` /
`BENCH_MODE`, JSON error shape, `{"error":{"code","message"}}`, unified
validation precedence, no 5xx on any input.

## How to run it

```bash
# from the directory containing ledger/ (or from ledger/ itself; both work)
PORT=8080 DB_PATH=/tmp/ledger.sqlite3 BENCH_MODE=1 python3 ledger/server.py
curl -s http://127.0.0.1:8080/health

# the bench test suite (talks to the running instance only)
BASE_URL=http://127.0.0.1:8080 python3 ledger/tests/run_tests.py
```

`bench.json`'s `start` is:

```json
"exec python3 -c 'import os,runpy,sys; p=\"ledger/server.py\" if os.path.exists(\"ledger/server.py\") else \"server.py\"; sys.argv=[\"server.py\"]; runpy.run_path(p, run_name=\"__main__\")'"
```

That odd-looking form is deliberate: `exec` replaces the launcher shell with
Python, so the PID the benchmark starts **is** the server. A plain
`python3 ledger/server.py || python3 server.py` pipeline leaves Python as a
child of the shell; SIGKILLing only the launched PID then orphans a process
holding `PORT` and the restart fails with `EADDRINUSE`. This was found by an
independent audit and is verified on Linux from both working directories.

## How it was verified (real runs, not just code review)

* **Conformance:** `tests/run_tests.py` — 27 black-box tests covering every
  endpoint, status/error code, validation precedence, idempotent replay
  (byte-identical body + `Idempotent-Replay: true`), mismatch, key reuse after
  4xx, key-length boundaries, concurrent same-key requests, concurrent
  deposits/transfers/reversals, global `seq`, default page size 50, pagination
  boundaries, bank summary, ledger invariants, protocol-level junk, and reset.
  Passed on Windows (Py 3.12.14) and Linux/WSL (Py 3.12.3).
* **Crash durability:** `tools/durability_check.py` starts its own instances.
  Phase 1: deposit → 201 → hard kill → restart on the same `DB_PATH` → balance,
  entry and byte-identical idempotent replay are all still there. Phase 2: six
  threads fire deposits/transfers/reversals, the process is SIGKILLed
  mid-flight, restarted, and then every recorded 2xx is replayed and the whole
  ledger is re-validated (per-account sum of entries == balance, `total ==
  deposits`, each transfer/reversal exactly two opposed entries, `balance_after`
  chain, no negative balance, no torn transfer). Passed with real `SIGKILL` on
  Linux and `TerminateProcess` on Windows.
* **Concurrency:** 20 parallel transfers of 100 from a 1000 balance →
  exactly 10 succeed, 10 get `422 INSUFFICIENT_FUNDS`, balance never negative;
  12 parallel reversals of one transfer → exactly one 201, the rest
  `409 ALREADY_REVERSED`; 8 parallel same-key deposits → one execution, money
  moved once.
* **Mutation check:** 19 single-bug mutants of the service (wrong entry sign,
  missing replay header, broken pagination offset, no funds check, per-account
  `seq`, default limit 200, non-verbatim replay, missing reset, etc.).
  `tests/run_tests.py` catches 16 of them; the 3 not caught are
  persistence-only defects (idempotency not persisted / not atomic with the
  money movement / `synchronous=OFF`) that a live-server test cannot observe by
  design — those are exactly what `tools/durability_check.py` covers.
* **Independent red-team audit** (separate agent, fresh context, read-only on
  `ledger/`): ~3,700 assertions on Windows and Linux — spec 467/467,
  adversarial robustness 129/129 with **zero 5xx and zero tracebacks**,
  concurrency 465/465, kill -9 durability 2590/2591 (the single miss was an
  informational WAL-copy check, not a spec item). It found and I fixed:
  4301+-digit `limit`/`after` → 500, malformed absolute-form request target
  (`urlsplit` ValueError) → 500, lone-surrogate JSON strings → 500, deeply
  nested JSON → 500, HTML error bodies for stdlib rejections, bad HTTP version
  producing a headerless 505, the start-command PID issue, and four test gaps.
  Remaining audit items are documented ambiguities, not defects.
* **Linux end-to-end:** the exact `start` and `test` commands from
  `bench.json`, from both working directories, then `kill -9` of the launched
  PID, restart on the same `DB_PATH`, invariants checked — all pass.

## What I would most like you to look at

1. **`store.py` + `service.py` durability contract**: every request is one
   `BEGIN IMMEDIATE … COMMIT`; the idempotency record is written *in the same
   transaction* as the balance changes and ledger entries; the HTTP response is
   only written after `COMMIT` with `synchronous=FULL`. That makes "2xx implies
   durable" structural rather than best-effort, and makes replay-after-restart
   exact.
2. **`service.Ledger._idempotent`** — the single choke point for the three
   money-moving POSTs: lookup → fingerprint check → execute → store, all under
   the global lock, so concurrent same-key requests execute once and a 4xx
   never occupies the key.
3. **`DECISIONS.md`** — especially validation precedence, `from == to` vs
   missing account, idempotency fingerprint definition, reset semantics, and
   what the black-box test command can and cannot see.
4. **`bench.json` start command** — the `exec` trick that keeps the server's PID
   stable under the benchmark's SIGKILL/restart cycle.
5. **Protocol hardening in `api.py`** — the service answers every malformed
   request (bad request line, bad version, malformed URL, unknown method,
   4,300+-digit query values) with a JSON 4xx instead of the stdlib's HTML or a
   500/traceback.

## Known limitations / intentionally not done

* One process per database file; no coordination between multiple service
  instances sharing a `DB_PATH` (the in-process lock assumes one writer).
* `DB_PATH` designates the SQLite file *and its `-wal`/`-shm` sidecars*; after
  `kill -9` acknowledged rows may still live in `-wal` (the contract's "restart
  with the same `DB_PATH`" recovers them). Copying only the main file while
  the service runs would lose them.
* No authentication, authorisation, TLS or rate limiting (meant for an internal
  network behind an authenticated proxy); accounts cannot be deleted; owners
  are not unique; ids are opaque random strings.
* The benchmark `test` command is, by contract, a live-server suite and cannot
  restart the service, so persistence/atomicity are verified by the separate
  `tools/durability_check.py` rather than inside the test command. This split
  is documented in README/DECISIONS.
* Developed and exercised on Python 3.12 (Windows and Linux/WSL); the code uses
  no feature newer than Python 3.11, which is the grader's target.
