## 2. 实现要点（对应“愿望”部分）

- **ETag 是内容强校验器**：`"<对象字节的 sha256>"`，与名字、时间无关；相同内容必相同，不同内容必不同，跨重启稳定。
- **Last-Modified 只在真变化时更新**：字节与 `Content-Type` 都相同则视为同一版本；`X-Bench-Now` 控制写入时间（截断到秒，支持时区偏移，非法格式 400）。JSON 的 `modified` 与 `Last-Modified` 是同一秒精度时刻。
- **单一对象上的检查与提交是原子的**：每个对象一把异步互斥锁；`If-None-Match: *` 与 `If-Match: <etag>` 的“检查 + 写入”在锁内完成，并发覆盖/并发创建恰好一个成功、其余 412（自测里用真正的并行请求验证）。
- **写入先落盘再响应**：请求体流式写入临时文件 → `fsync` → 原子 `rename` 到内容寻址目录（`<sha256>` 文件名）→ 原子替换元数据 JSON（`fsync` 后 rename）→ 才发响应。崩溃最多留下孤立内容文件，元数据永不指向半截数据；启动时清理临时文件并 GC 无引用内容。
- **内容去重 + 引用计数 GC**：同内容多名字只存一份；删除/覆盖后仅当无记录引用、无下载 pin、无在途上传时才真正删除字节文件（下载期间 pin 住，避免“删到正在读的文件”）。
- **不爆内存**：上传边读边哈希边落盘、超限即 413；下载用 `createReadStream` 直接按范围流出，`Content-Length` 与实际返回字节严格一致。5 MiB 上限按规格实现，且注意了“失败的写入不影响旧版本”。
- **URL 手工解析**：避免 WHATWG URL 规范化 `%2e%2e`，从而能按要求对解码后的 `.`/`..`/斜杠等返回 400；统一错误体 `{"error":{"code","message"}}`，实测无 500、无堆栈泄漏。

## 4. 已知限制（诚实说明）

- 单进程假设：互斥锁在进程内，不支持多个进程共享同一 `DB_PATH`（无跨进程文件锁）。
- 元数据常驻内存并整体原子重写（O(对象数)/次写入）。对内部资源桶足够，不适合百万级对象。
- 对象大小上限 5 MiB（规格要求）；更大的请求会被读完丢弃后返回 413（保证连接健康且旧版本不变）。
- 按规格只支持单段 Range；多段 Range 一律忽略并返回 200 全量；HEAD 忽略 Range。
- 没有鉴权、TLS、压缩、多节点复制——不在任务范围内，部署时应放在内部代理/鉴权之后。
- `HEAD` 的错误响应没有响应体（HTTP 语义如此），只有状态码与头部。
- 本机验证环境是 Windows + Node 24；目标评测环境为 Linux + Node 22。实现只用跨平台标准库 API，路径处理用 `path.join`，目录 `fsync` 在 Windows 上被吞掉（文件已先 `fsync`），Linux 上会正常 `fsync` 目录。
