# FINAL_MESSAGE — 带租约的作业队列

## 交付了什么

`job-queue/` 是一个**零依赖的 Node.js 作业队列**（只用标准库，`setup` 为空，一条命令启动），
实现了规格里全部接口与规则：入队 / 租用 / 确认 / 失败重试 / 续租 / 死信 / 死信复活，
并保证**数据在响应之前就已落盘**（`kill -9` 后用同一个 `DB_PATH` 重启，状态原样恢复）。

```
job-queue/
├── bench.json              # start / setup / test / health
├── package.json            # 无运行时依赖
├── package-lock.json
├── README.md               # 启动、接口、配置、语义、持久化说明
├── DECISIONS.md            # 规格没说清楚的地方：我的取舍与理由
├── src/
│   ├── server.js           # HTTP 层：路由、校验、错误信封、落盘屏障
│   ├── queue.js            # 领域层：状态机、租约、ack/nack/extend/requeue
│   └── persistence.js      # 写前日志（WAL）、fsync、快照压缩
├── test/run.js             # 基准测试命令（只连 BASE_URL，不自己起服务）
└── scripts/
    ├── durability-check.js # 手动：飞行中 kill -9 的崩溃测试
    ├── load-check.js       # 手动：1200 轮压测 + 压缩 + 重启
    └── mutation-test.js    # 手动：13 个“故意改错”的实现，测试必须全部报错
```

## 怎么运行

```bash
cd job-queue
PORT=8080 DB_PATH=/var/lib/jq/queue.log BENCH_MODE=1 node src/server.js
# 另一个终端
BASE_URL=http://127.0.0.1:8080 node test/run.js
```

`bench.json` 里写的就是这两条：`start: "node src/server.js"`、`setup: ""`、
`test: "node test/run.js"`、`health: "/health"`（启动命令假定工作目录是 `job-queue/`）。

## 怎么验证的（全部是我实际跑出来的结果）

| 验证 | 结果 |
|---|---|
| 净室复现：拷贝到新目录 → 用 bench.json 的 start 起服务 → health 200 → 跑 test | **34 passed, 0 failed**，退出码 0，服务端 stderr 为空 |
| `scripts/durability-check.js`：请求飞行中 `SIGKILL` → 同 `DB_PATH` 重启 | 客户端**已收到响应的 20/20 个作业全部还在**（`state: done`），重启后 enqueue/lease/ack 照常可用 |
| `scripts/load-check.js`：1200 轮 enqueue→lease→ack | 8.7s（约 2.4ms/请求，瓶颈是 fsync）；触发日志压缩成快照；**重启后 1200/1200 状态完好** |
| `scripts/mutation-test.js`：13 个单点改错的实现 | **13/13 全部被测试抓到**（优先级取反、租约过期边界差一、nack 忽略重试延迟、ack 不校验 token、死信顺序取反、`max_attempts` 差一……） |
| 手动核对 | `POST /api/__bench/reset` → 200 且日志被截断为 0 字节、stats 全零；同 `DB_PATH` 重启后 `done` 状态保留；`BENCH_MODE` 未设置时 reset 返回 404；`GET /health` 恒 200；并发 5 个 worker 抢 1 个作业 → 恰好 1 个 200、4 个 204、attempts 只加 1 |

规格里我逐条对照过的地方：租约过期是**含边界**的（`now >= lease_expires_at` 立即失效）；
过期后 `attempts < max_attempts` 回到 `ready` 且 `run_at` 变成租约到期时刻，否则进死信
且 `last_error = lease_expired`；nack 退避是 `min(1000 × 2^(attempts−1), 60000)`；
`ack/nack/extend` 的三种 409（`LEASE_MISMATCH` / `LEASE_EXPIRED` / `ALREADY_FINISHED`）都按
“令牌是不是最近一次租约的令牌”区分；死信列表按**进入死信的先后**排序（按虚拟时间，
租约过期死亡取 `lease_expires_at`，nack 死亡取请求的 now）；`requeue` 把 `attempts` 归零、
立即可取并清掉 `last_error`；任何非法输入都只返回 400/404/409，不会有 500、不会漏栈。

## 三个我比较满意的设计决定

1. **状态是“推导”出来的，不是被定时器清扫出来的。**
   作业记录只存事实（`phase` / `lease_expires_at` / `attempts` / `run_at`），
   客户端看到的 `state` 是「记录 + 本次请求的 now」的**纯函数**（`src/queue.js` 的
   `stateOf` / `runAtOf` / `leaseStatusOf`）。所以没有任何后台时钟，每个接口看到的
   状态天然一致，服务停机期间过期的租约在下一个请求里自动归位，评测里的虚拟时钟
   （`X-Bench-Now`）也天然被支持——包括时间倒流的情况。

2. **落盘屏障在响应之前。**
   每次变更 = 追加一行 WAL 记录 → `fsync` → 才写 HTTP 响应（`src/server.js` 的 `handle()`）。
   于是 `kill -9` 唯一能弄丢的，是客户端**没收到响应**的那次操作——这正是“至少一次投递”
   该有的语义窗口：作业等租约过期后会被重新投递。

3. **租用的原子性靠“单线程 + 同步临界区”。**
   请求体读完之后，选作业、加 `attempts`、发 token、写 WAL、响应这一整段没有任何
   `await`，Node 的事件循环天然把它变成互斥区，所以并发 worker 不可能拿到同一个作业，
   不需要锁、不需要事务、也不需要 CAS。

## 没做完的 / 已知限制

- **一个 `DB_PATH` 只能由一个进程拥有。** 文件格式没有跨进程锁；要横向扩展就每个进程
  一个数据文件（这在 `DECISIONS.md` 里写明了）。
- **`done` / `dead` 的作业不会自动回收**——规格没有 TTL，而且 `stats` 要报 `done`，
  删掉会改变可观察行为；数据文件只能靠 `reset` 或压缩变小。
- **没有鉴权、没有限流、没有多租户隔离**，这是规格之外的。
- **入队没有幂等键**（规格的作业模型里没有这个字段），所以重复 POST 会产生多个作业；
  “至少一次”是在 worker 侧（租约过期重投）实现的。
- **每次变更一次 `fsync`**，约 1–2ms；量大时这是主要开销（1200 轮 8.7s）。
- 启动命令假定工作目录是 `job-queue/`（`node src/server.js`），换目录启动需要写全路径。

## 最想让你看的地方

1. `job-queue/src/queue.js` 里的 `stateOf` / `runAtOf` / `leaseStatusOf` 三个函数——
   整个语义（延迟、就绪、租用、过期、死亡）都压在这几十行“纯函数”里，几乎没有可变状态，
   这也是我敢让 `X-Bench-Now` 直接参与业务计算的原因。
2. `job-queue/src/server.js` 里 `handle()` 末尾那段“**先 fsync 再响应**”的屏障，以及
   `job-queue/src/persistence.js` 里压缩时的“临时文件 → fsync → 原子 rename → 再截断日志”
   顺序——这两处是崩溃安全的全部要害。
3. `job-queue/DECISIONS.md`：规格里 20 处含糊的地方（`payload` 是否必填、`extend` 的
   `lease_ms` 是否必填、token 缺失该 400 还是 409、死信排序用检测时间还是虚拟时间、
   未知路由该 404 还是 405……）我都写明了取舍和理由。如果评测的期望和我的判断不一致，
   这一页是改起来最快的地方。
