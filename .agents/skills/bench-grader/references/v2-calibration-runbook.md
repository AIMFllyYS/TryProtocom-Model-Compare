## 2. 提示词三档消融（待恢复评测后才能跑）

目的：看“契约 + 愿望”会不会比旧的完整约束提示词更差，以及愿望层本身有没有收益。

三档，用同一份契约，只改变愿望和约束：

- A 档：只保留契约。删掉愿望段。
- B 档：v2 正式提示词，契约加愿望。这是要上线的版本。
- C 档：v1 风格，把实现手段、输出格式、禁止事项都写进提示词。

选题四道，覆盖不同能力，不要八道全做：

- 创作：V01（单页）和 V05（大体素建筑）。
- 从零实现的后端：B3 或 B8，二选一。B8 更贵，时间紧就用 B3。
- 遗留调试：B6。

样本：每一档每一题 3 次，全程同一个模型，不混入别的模型的结果。记录总分、各维度分、用时、成本、Tier0 是否通过。三次都算，不因为低分重跑。准备试跑、用户中断、环境启动失败不算正式样本。

怎么读：

- B 档的质量中位数不应低于 C 档。若低于，愿望化把能力做差了，要收回愿望里含糊到无法交付的句子，而不是加回实现清单。
- A 档与 B 档的差距是愿望层的收益。差距接近 0，说明这道题的分数主要来自契约，愿望可以再写得更具体（仍然不限制手段）。
- B 档方差明显大于 C 档时，不要靠加约束压方差。完整版榜单用稳定性轴呈现。

## 3. 多模态与人工一致性（待恢复，且已有作品之后）

从创作类作品里抽 20 个（不足 20 个就全部抽）。每个交互检查项同时记下人工结论和多模态预填结论。一致率按“检查项”而不是按“作品”算。

某一项一致率低于 80%：重写该项的锚点，或把它降成只由人打分，并从预填请求里拿掉。预填始终不自动写入 `manual_scores.json`。

## 4. 检查项分析（待有正式样本之后）

对已有运行：

- 方差接近 0 的自动项：所有模型都满分或都零分。都满分的项没有区分度，降权或并入别的项。都零分的项先确认是不是测试或环境写错，再决定留不留。
- 与总分负相关的项：先看是不是“写了测试所以变慢”这类误伤，再改规则，不要直接删。
- 把待修订项列成清单，改 rubric 之后用 `validate-rubrics` 和对应题的 `backend-check` 再跑一遍。不重算 v1 历史分。

## 5. 上线顺序（待恢复之后）

与仓库根目录 `AGENTS.md` 一致：

1. 先简化版。每个候选模型、每道 v2 题默认测 1 次。榜单取该模型该题已有正式样本里的最高分，并标注样本数 n。不得为了抬分重跑。
2. 同一模型最多大约 3 道题同时跑。不要同时切到下一个模型。
3. 简化版覆盖完候选清单之后，再对选定模型把每道题补满 3 次，生成完整版榜单。不满 3 次的不进完整版。3 次都计入稳定性，不剔除低分。
4. 只有事故允许重测。用 `bench.py mark-incident` 登记。事故类型见 `benchmark.yaml` 的 `v2.incident_kinds`：tier0、harness、interrupted、other。
5. 准备试跑、用户中断、环境起不来，都不算完整正式样本。
6. 冻结 v2.0 要用户同意。同意之后才把 `config/benchmark.yaml` 里 `v2.version` 从 `v2.0-draft` 改成 `v2.0`，并填写 `v2.frozen_date`。冻结前再跑一遍 `validate-rubrics`。不要迁移或重算 v1。

## 6. 启动前检查清单

恢复评测之前，逐项打勾：

- 用户明确说了恢复。没有这句话，停在本手册。
- `python bench.py validate-rubrics` 通过。
- `python -m pytest -q tests` 在 `scripts/` 下全过。
- `python bench.py backend-check B1` 到 `B8` 全部 `ok`。B3 的 `api.chaos_ok` 为 true。B4 的 `api.persist_ok` 为 true 且 `api.diff_match_ratio` 为 1。B5、B6、B7、B8 的 `--defect` 为 `ok`。
- 评测机固定：同一台机器、同一个渲染器。帧率只在同一渲染器下比较（`v2.environment.require_same_gl_renderer`）。
- 各题 `time_limit_min` 是软时限：超时不中断、不扣质量分，只记用时。
- `tasks/*/hidden/` 没有出现在 `materials/` 或将要复制给模型的目录里。`.agents/skills/bench-grader` 镜像不含 `hidden/`。
- B7 的速度阈值是在空闲的这台机器上复核过的。负载下测出的 p95 不拿来改阈值。
