# FINAL_MESSAGE

## 一句话

在 `reportdesk/` 原项目上做了一次完整的「先测量、再定位、后优化、每步复测」的性能改造：接口行为（数字、字段、排序、状态码、错误格式）与优化前完全一致，20k 数据下报表接口冷读快 10–45 倍、写路径快 22–46 倍，16 并发 p50 从 630ms 降到 1.8ms；并给出了 10 倍数据量的实测验证、逐项收益、失效场景和可复跑的测量工具。最终 `app.py` sha256 = `FA1EBCD8C374F953ACCA7ADEBAF641127F941ACA5BB99BDAFD270E0A494B77BA`。

## 怎么做的

1. **先复现和量化**：冻结原始实现作 oracle，用 harness 测各接口 cold/hot 与并发。原始实现 `top-products` 全区间一次请求要跑 **18456 条 SQL**（其中 18454 条是逐订单明细点查），`monthly`/列表/建单都全表扫描；再加上 `with LOCK:` 包住整个 `route()`，吞吐被钉死在 ~24 req/s、p50 随并发线性涨。
2. **三个根因 → 六项优化**（`PERF-REPORT.md` 第 3 节逐条给了代码位置和前后数字）：
   - N+1 → 单条 SQL 聚合 + 5 个索引/覆盖索引（明细查询不回表）；
   - 全表 Python 扫描 → 索引范围扫描 + SQL 聚合（日期比较改成索引友好的字符串区间，语义仍是两端含）；
   - 报表 O(订单数) → 增量维护的月粒度预聚合 `monthly_stats` / `product_monthly`，`top-products` 任意区间按「首月残段 raw + 中间整月预聚合 + 末月残段 raw」拼；
   - 全局锁 → 去掉，每线程独立连接 + WAL，读请求包一个只读事务保证响应内部快照一致；
   - 写路径 → `BEGIN IMMEDIATE` 短事务，并发创建不丢单/不重号；
   - 只读结果做「写版本号 + `PRAGMA data_version`」双重校验的缓存，任何写提交后立即失效（不撒谎）。
3. **每改一处就复测**：行为用差分对拍确认没变，性能用交错配对测量（同机同窗口 A/B 交替，抵消共享机器 2–4 倍的负载漂移）。

## 核心结果（20k 数据，cold=reset 后首读，配对测量；详见 PERF-REPORT）

| 接口 | BEFORE | AFTER | 收益 |
|---|---:|---:|---:|
| top-products 全区间 | 159.8 ms | 7.4 ms | 21.6× |
| top-products 单月 | 48.3 ms | 1.5 ms | 32× |
| monthly 2026 | 29.4 ms | 0.66 ms | 44.5× |
| orders 首页 / 按客户 | 29.7 / 24.5 ms | 3.6 / 1.1 ms | 8.2× / 21.4× |
| 客户汇总 1 / 7 | 24.4 / 23.6 ms | 2.4 / 1.4 ms | 10.1× / 17.3× |
| 建单 / 取消 / 改价 | 45.8 / 37.9 / 4.1 ms | 2.1 / 0.83 / 1.4 ms | 22.3× / 45.6× / 3× |

并发（混合读负载，每档 120 请求）：BEFORE 吞吐恒定 22–25 req/s、16 并发 p50 630ms；AFTER 1–4 并发 1008–1911 req/s、16 并发 p50 1.8ms（348×）。

10x 数据（20 万订单 / 697,640 明细）：top-products 全区间 1618→7.4ms（219.8×）、monthly 254→1.4ms（176.8×）、建单 433→4.0ms；报表耗时与订单总量解耦，订单列表/客户汇总仍随相关行数线性但常数很小（orders 首页 27ms，主要是契约要求的 `COUNT(*)`）。

## 怎么验证的（都是真实跑过的）

- **行为零差异**：red-team 用 772 个请求的矩阵（含错误码/边界日期/分页 tie/X-Bench-Now 极端值/50 连写+取消/并发写读）对原始实现 vs 优化实现严格比较（status+JSON 值+类型+键顺序）：**0 差异**；我自己的 64 用例 + 309 随机用例 + 19 步写序列差分也是 0；10x 库上 14 个只读请求逐字节相同。
- **回归测试**：`reportdesk/tests/` 211 条，在**原始服务**上 211 passed（无假阳性），在**优化服务**上 211 passed；覆盖全部接口数值/排序/错误 message 原文/JSON 字段顺序/中文不转义、日期区间两端、monthly 12 个月、paid-only 口径、写后立刻读的新鲜度、8 线程并发创建不丢单不重号。
- **测试杀伤力**：red-team 造了 44 个「原始实现 + 常见提速回归」变异体和 23 个「优化实现 + 针对新机制的回归」变异体，用独立 probe/本测试套件逐个验证能抓到（报告见消息记录；常见回归如缓存不失效、日期端点开闭、按 units 排名、tie-break 反、total=本页、非 paid-only、改价改历史、丢 items 等全部被抓到）。
- **并发正确性**：16 线程并发创建 320 单（169.6 单/秒）无 500、id 无重复（20001..20320）、每单金额/明细/总数/报表与独立模型一致；并发取消（含 409 双取消）正确。
- **10x 正确性**：预聚合结果与直接 SQL 聚合（订单×明细 raw）在 20 万订单/70 万明细上逐项一致，monthly/top-products 全部对得上。
- **迁移**：把原始实现生成的旧库直接交给优化版启动（自动建预聚合表/索引）后，7 个接口与原始服务逐字节相同。

## 没做 / 不确定（如实）

1. **8/16 并发下 AFTER 的 p95 毛刺**（186–363ms，p50 仍 1–2ms）没有定位到单一原因，报告 6.3 标为待查；推测是共享机器（测量期间系统负载 ~99%、同机还有其它 benchmark）与客户端 GIL 的共同作用，但没证据，所以不写死结论。
2. **预聚合表是单写者假设**：`monthly_stats`/`product_monthly` 只由本服务在写事务里维护；如果有其它进程直接写 `orders`/`order_items`，报表会失真。多实例共享同一 DB 时，缓存有 `PRAGMA data_version` 兜底但属于 best-effort，不是强一致保证。这些都写进了 PERF-REPORT 第 10 节。
3. **深翻页仍是 O(offset)**：接口契约要求返回 `total` + `offset`，没改成游标分页；10x 下 unfiltered 列表首读 27ms 主要花在 `COUNT(*)` 上。如果以后要冲更大数据量，这是第一优先级（可用计数预聚合）。
4. **reset 变慢**：reset 是 `BENCH_MODE=1` 的评测辅助端点，不是业务接口。20k 下 BEFORE 308ms / AFTER 382ms（同量级，AFTER 多了预聚合重建）；10x 库第一次 reset 要把 90 万行截断回 2 万，会到秒级（报告 7.3 分场景写清）。它不影响任何业务接口延迟，但如果评测按「每次 reset 后计时」跑，会看到这段成本。
5. **测试抓不到的少数纯竞态变异体**：如「GET 不包读事务」「缓存版本号在 COMMIT 前推进」这类只在特定交错下才暴露的缺陷，顺序测试和常规并发测试可能抓不到（red-team 会给出最终盲区清单）。这是测试的边界，不是服务的已知问题。
6. **`X-Bench-Now` 的 naive 时间按服务器本地时区解释**：这是原始实现的行为，我原样保留；跨时区部署时语义会随机器时区变（优化前后一致，只是提醒）。
