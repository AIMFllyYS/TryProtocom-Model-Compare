# FINAL_MESSAGE

## 我做了什么

把 `reportdesk/` 这个「功能对但很慢」的销售报表服务，在**不改动任何接口返回值**的前提下重做了一遍读路径和并发模型。
所有改动都在 `reportdesk/` 里，运行时仍然只用 Python 标准库，`seed.py` 一个字没改。

三件事，按重要性：

1. **把「每次请求全量现算」换成「预先算好、按需读取」。**
   新增 5 张物化汇总表（按日/月的商品销量销售额、按客户统计），建单和取消订单时
   **在同一个事务里**把它们一起更新。`top-products` 的区间聚合因此从 O(订单数)
   变成 O(月份数 × 商品数)。

2. **把过滤/排序/聚合下推给 SQL，加覆盖索引**，干掉原来的 N+1
   （一个 `top-products` 请求原来要发 18638 次明细查询）和「全表拉进 Python 再筛」。

3. **把一把把所有人串行掉的全局锁拆成读写分离的锁**（读共享、写独占），
   加连接池 + WAL。这就是运营说的「一多人用就转圈」的直接病因。

## 怎么验证的

* **返回值一字不差**：`bench/golden.py` 采集 73 个请求（含建单、取消、改价、补录历史订单、
  以及各种 400/404/409 错误分支）的完整响应，在基线服务和优化后服务各抓一份，
  逐条比对 → `OK: all 73 steps identical`。原始响应头和响应体也逐字节比对过
  （`bench/compare_raw_http.py`）。
* **拿原始实现当参照实现**：`tests/test_perf_regression.py` 里 `import baseline_app`
  （`bench/baseline_app.py` 是优化前 `app.py` 的逐字副本），在内存库里灌同一份种子数据，
  然后把服务返回的月度报表 / 商品排行 / 客户汇总 / 订单列表 / 错误码
  跟参照实现逐字段比对。汇总表算错、月份边界切错、取消订单没回滚，都会被抓住。
* **新鲜度**：新建、补录历史订单、取消订单、改价之后，下一次读取必须立刻反映
  （明确断言月度报表的订单数和金额回滚到位）。
* **并发**：16 个线程同时建单，全部 201、订单号不重复、`total` 恰好 +16、
  月度汇总恰好 +16；并发读看不到半套数据。
* **测试有没有牙**：我做了几个**故意带提速回归**的服务版本
  （`bench/regressed_app.py`），把 `tests/` 跑在它们上面：
  缓存不失效 / 取消不回滚汇总 / 建单不更新汇总 / 退回 N+1 / 删索引 /
  写路径既没事务也没锁 —— **6 种全部被抓到**。
* **多实例与重启**（`bench/check_multiinstance.py`）：两个进程共用同一个 `DB_PATH`，
  A 写入 B 立刻读到，反之亦然；两边同时写订单号不重复；重启后数据和汇总都在。
* **10 倍数据**：`bench/gen_big.py --scale 10` 造 20 万订单 / 69.7 万明细，
  对比基线与优化后的表现（数据见 PERF-REPORT 第 6 节）。

## 没做完 / 不确定的

* **没有做多进程 / 多 worker**。`ThreadingHTTPServer` 一个连接一个线程，
  CPU 活受 GIL 限制。再往上要换 `fork` + SO_REUSEPORT，会引入多实例一致性问题，我没动。
* **没有做「按商品预聚合的累计表」**。`top-products` 并发 p50（32 ms）主要耗在
  6300 行月表数据的 GROUP BY 临时 B 树上。再进一步可以给月表加 `(product_id, month)`
  二级索引消掉排序——我试了，SQLite 的查询计划器没改主意，收益约 0，所以没加。
  真要再快只能上累计表，代价是每次写要更新该商品之后所有月份的累计值，
  我判断不划算。
* **`/api/orders` 的 `total` 仍是 O(n)**（走覆盖索引，10 倍数据下约 4 ms）。
  要再快得维护计数器，暂未做。
* **`PRAGMA synchronous=NORMAL`**：我主动放松了「断电级」的持久性（进程崩溃不丢数据）。
  这是唯一一个我主动放弃的保证，要换回来改 `app.py` 里 `connect()` 的一行即可。
* **没有验证 100 倍数据量**（题面说的是 10 倍，我只验证到 10 倍）。
* **10 倍数据下原始实现的完整压测矩阵没跑完**：它单次报表请求要几十秒，
  并发矩阵跑太久，我改成定点测量（每个接口 1~5 次），细节见 PERF-REPORT 第 6 节。
* `bench/` 目录里留了一些测量用的脚本和 JSON 结果（不含大数据库文件），
  它们不参与运行时，可以整个删掉。

## 兼容性提醒（给评测/部署的人）

* `bench.json` 没动（`start` / `test` / `health` 都保持原样）。
* 数据库文件如果还是**旧版本服务留下的**（没有汇总表），新服务启动时会自动检测并整体重算
  汇总表，不用手工迁移；如果是指纹对不上（比如被别处改过），也会重算。
* 启动时会做一次指纹校验，20 万订单的库约 1 秒内完成。
