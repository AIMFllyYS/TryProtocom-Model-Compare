# B5 · 库存服务排查修复 · 最终说明

## 做了什么

在 `inventory-legacy/app.py` 上原样修复（没有重写，仍是纯标准库），
`ISSUES.md` 的 5 个问题 + #27 新需求全部处理，另修复了排查中发现的 1 个
ISSUES.md 以外的缺陷。详细根因见 `inventory-legacy/FIXES.md`，逐条摘要：

- **#12 超卖**：根因是 reservations / adjust / commit 三处"读-判-写"在
  autocommit 下不原子（audit 的 fsync 还拉大了竞争窗口）。新增 `write_tx()`
  （`BEGIN IMMEDIATE` + `with c:`）把三处写路径串行化。
- **#15 低库存慢半拍**：`item_view` 里 `avail < thr` → `<= thr`。
- **#18 翻页/总数**：`list_items` 原来 SQL 只 `LIMIT/OFFSET` 不 `ORDER BY`，
  排序在 Python 里只对当前页做；`total` 也不过滤 `q`。改为 SQL 内
  `ORDER BY <列>, sku`（主键决胜）+ 带 WHERE 的 `COUNT(*)`。
- **#21 估值差几分钱**：`int(p/100*s*100)` 浮点丢分 → 纯整数
  `SUM(price_cents * stock)`。
- **#24 注入**：`q` 被 f-string 拼进 LIKE（`' OR '1'='1' --` 可全表读、
  多语句注入会 500）。改参数化 `LIKE ? ESCAPE '\'`，启用了一直存在却没人
  调用的 `like_escape()`。
- **#27 低库存报表**：新增 `GET /api/reports/low-stock`，一条
  `LEFT JOIN`（只接未过期 held 预留）+ `HAVING avail <= threshold` +
  `ORDER BY avail, sku`，返回 `{items, count}`。
- **额外缺陷**：`reserved_qty` 收了 `now` 参数却从没过滤 `expires_ms`，
  过期 held 预留永久占库存。加 `expires_ms > now` 后，详情/校验/报表
  口径全部一致。

## 测试

- `tests/test_regressions.py`（新增，12 条）：每个修复一条"修复前失败、
  修复后通过"的回归测试；并发用例用 barrier 对齐后 10–20 线程真打服务。
- 原有 `tests/test_inventory.py` 未改动，全部通过。

## 验证方式

1. `PORT=8080 DB_PATH=test.db BENCH_MODE=1 python app.py` 起服务；
   `python -m unittest discover -s tests -v` → **18/18 通过**。
2. 把修复前的 `app.py` 原样跑在 8090 端口跑同一套测试 → 12 条新增回归
   测试**全部失败**（并发超卖、边界、翻页、分、注入 500、报表 404、
   过期占位），确认每条都真的抓得住缺陷；原有 6 条不变绿（证明没误伤）。
   验证用副本已删除。
3. curl 手测：`/health`、空报表 `{"items":[],"count":0}`、字面量 `%`
   搜索、注入串返回空列表且表完好。

## 没做好 / 不确定

- `commit` 过期预留时会在事务里先落 `state='expired'` 再报 409——行为与
  原版一致，只是现在显式提交了这步状态迁移。
- 并发测试在无缺陷版本上是"必然失败"级别的窗口（audit fsync 保证），但
  `test_concurrent_commit_only_once` 的竞争窗口最窄，极端调度下理论上可能
  偶发不触发——保留它因为它本身也是正确性校验。
- `reserved_qty` 修好后，`held` 但已过期的预留在库里仍显示 `held` 状态
  （惰性迁移），只是不再占库存——语义正确，展示层如果要严格一致可再懒迁移。
